# 量化系统架构边界

**创建日期**：2026-06-07  
**目标**：让量化策略模块长期保持高内聚、低耦合，避免数据、策略、AI、执行和页面逻辑互相缠绕。

---

## 1. 当前判断

当前量化策略实验室的方向是合理的：先有真实历史数据，再做策略筛选、模拟盘、资金分配和干预。但现阶段仍是功能跑通型架构，部分 controller 和前端页面承载了太多职责。

长期优化目标不是马上拆成微服务，而是先拆出清晰模块边界。每个模块只关心自己的领域，通过稳定的数据结构交互。

---

## 2. 推荐分层

```text
UI Layer
  展示历史数据、策略配置、筛选记录、组合建议和人工干预入口

Application Layer
  编排一次完整任务：读取数据 -> 运行策略 -> 保存结果 -> 返回页面视图模型

Data Layer
  历史行情、实时行情、新闻事件、账户流水、原始数据和交易时段清洗后的数据质量报告

Research Layer
  指标计算、策略定义、回测引擎、压力测试、评分模型

Portfolio Layer
  资金权重、风险预算、策略组合、凸优化

Execution Layer
  模拟盘、实盘订单、拆单、风控开关、人工/模型干预

AI Layer
  新闻摘要、事件归因、参数建议、风险解释
```

---

## 3. 依赖方向

允许的依赖方向：

```text
UI -> Application -> Domain Services
Application -> Data / Research / Portfolio / Execution / AI
Research -> Data Types only
Portfolio -> Research Results only
Execution -> Portfolio Decision + Risk Rules only
AI -> Read-only Context + Suggestion DTO
```

禁止的依赖方向：

1. 策略逻辑不能直接读取 CSV、MongoDB、Twelve Data 或新闻接口。
2. AI 不能直接修改策略源码，不能直接下单。
3. 前端不能自己拼回测规则，只能提交配置。
4. 执行层不能反向改策略评分，只能消费已确认的策略/组合结果。
5. 数据层不能知道某个策略如何交易，只负责标准化、缓存和质量报告。

## 4. 核心接口

### MarketDataset

历史行情统一输出：

```typescript
interface MarketDataset {
  symbol: 'xauusd';
  period: '1m' | '5m' | '15m' | '1h' | '4h' | '1d';
  candles: Candle[];
  meta: {
    provider: string;
    source: 'live' | 'cache' | 'stale_cache' | 'unavailable';
    candleCount: number;
    startTime?: string;
    endTime?: string;
    quality: DataQuality;
    session: TradingSessionQuality;
  };
}
```

策略和回测只接收 `MarketDataset`，不关心数据来自 GitHub、Dukascopy、Twelve Data 还是本地 JSONL。

数据层要同时保留两个概念：

- **Raw Dataset**：原始导入数据，用于审计、追溯和重新清洗。
- **Tradable Dataset**：按交易时段过滤后的可交易 K 线，策略筛选和回测默认只消费这一层。

### StrategyDefinition

策略定义必须包含：

- 策略 ID。
- 参数默认值、上下限和步长。
- 入场规则说明。
- 风控规则说明。
- 运行函数。

策略参数可以被人工或 AI 建议覆盖，但必须先经过上下限裁剪，再进入回测。

### BacktestRun

一次回测必须保存：

- 数据周期、数量、起止时间和来源。
- 策略参数快照。
- 滑点、手续费、仓位规则。
- 训练/验证分段表现。
- 压力测试结果。
- 最大回撤、PF、收益、样本警告。

## 5. 模块拆分建议

第一阶段先在现有 Node.js 后端内拆模块，不引入额外服务：

```text
src/modules/market-data/
  historyRepository.ts
  dataQuality.ts
  providers/

src/modules/research/
  strategyRegistry.ts
  backtestEngine.ts
  strategyScreening.ts
  scoring.ts

src/modules/portfolio/
  allocationModel.ts
  riskBudget.ts

src/modules/execution/
  paperBroker.ts
  interventionStore.ts
  riskGate.ts

src/modules/ai-assistant/
  strategySuggestion.ts
  newsInterpretation.ts
```

当前已有代码可以逐步迁移，不需要一次性重构：

- `marketHistoryStore` 保持数据仓库角色。
- `goldHistoryService` 逐步改成 `historyRepository` 门面。
- `strategyScreening` 拆为策略注册表、回测引擎和评分器。
- `strategyLab controller` 只保留请求校验和应用层编排。
- `ResearchCenter` 前端只展示视图模型，不承载策略规则。

## 6. 数据和策略的生命周期

1. 导入或刷新行情。
2. 写入历史仓库。
3. 生成原始数据质量报告和交易时段清洗报告。
4. 用户选择周期、样本量和策略参数。
5. 历史数据门面输出可交易 K 线。
6. 回测引擎运行策略。
7. 评分器生成推荐。
8. 保存 `StrategyScreenRun`。
9. 人工查看后，选择是否进入模拟盘或组合权重模型。

任何一步失败，都应该保留明确状态，不使用模拟数据补收益。

## 7. 长期演进路线

### V1：模块化单体

目标：先把边界拆清楚，所有代码仍在一个 Node.js 服务内。

适合现在阶段，开发和部署成本低。

### V2：Python 量化引擎

当需要 `cvxpy`、`hmmlearn`、大型回测和滚动窗口优化时，把 Research/Portfolio 计算移到 Python worker。

Node.js 负责用户、权限、任务调度和结果展示；Python 负责重计算。

### V3：任务队列

当一次回测超过数秒，加入队列：

- API 创建任务。
- Worker 执行回测。
- 前端轮询或订阅进度。
- 结果落库后可复盘。

### V4：实盘执行隔离

实盘执行必须单独隔离：

- 独立权限。
- 独立风控。
- 独立审计。
- 默认只接受经过人工确认的策略组合。

## 8. 当前下一步

短期最应该做三件事：

1. 在页面展示历史数据清单和策略筛选历史记录。
2. 做数据缺口扫描、交易时段清洗和补洞计划，避免长样本质量被误读。
3. 把 `strategyScreening` 拆出策略注册表、回测引擎和评分器，减少后续加策略时的改动面。
